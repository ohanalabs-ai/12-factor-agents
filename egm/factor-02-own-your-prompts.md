# Factor 02 — Own your prompts (EGM)

Upstream text: [`content/factor-02-own-your-prompts.md`](../content/factor-02-own-your-prompts.md) (unchanged). Everything below is OhanaLabs interpretation (Elephant and Goldfish
per the [EGM process](https://github.com/ohanalabs-ai/agentic-process/blob/main/docs/02-egm-first-principles-process.md)); the upstream text is the only source of what the factor says.

## Elephant

**Requirement.** The prompt that reaches the model is first-class code the team can read, version, test and change. A framework may help render it,
but the final token sequence is visible and controlled.

**Why.** The prompt is the primary interface between application logic and the model. If it is generated by an opaque abstraction, behaviour cannot be
reverse-engineered, diffed in review, or evaluated per change.

**Observable evidence.** Prompt text or templates in the repository; a way to print the exact rendered prompt for a run; prompt changes reviewed as diffs;
evals or fixtures that run against a prompt version.

**Smallest implementation.** A template file in git plus a function that renders it, a command that prints the rendered result, and at least one
regression eval per agent.

**Anti-patterns.** "role/goal/backstory" strings assembled by a framework with no way to inspect the result; prompts edited in a vendor console; prompts
with no tests; secrets or customer data pasted into prompts.

**What would change this.** If a managed runtime's built-in prompt demonstrably outperforms owned prompts and exposes the rendered text for audit, owning
the *inputs* to it (instructions, tool descriptions) may be enough. Test that claim with evals, not by assertion.

## Goldfish

Reviewer inputs: the agent definition files, the runtime config, a rendered-prompt sample, any eval directory.

| ID | Question | Evidence to look for | PASS | PARTIAL | FAIL |
|---|---|---|---|---|---|
| F02.1 | Is the agent's instruction text stored in version control next to the code or config that deploys it? | `.md`/`.yaml`/template files in git containing the instructions | all agents | some, or some only in a console/DB | none |
| F02.2 | Can the exact rendered prompt of a run be obtained? | a debug/print command, or a trace that records the final system+user content | yes, per run | only the template, not the rendered text | no |
| F02.3 | Do prompt changes go through review with a diff a human reads? | PR history touching the prompt files | yes | changes land without review for some agents | no history |
| F02.4 | Is there at least one automated eval or fixture that exercises the prompt and can fail? | eval script, golden outputs, rubric file wired to CI or a documented command | wired and failing on regression | exists, manual only | none |
| F02.5 | Are secrets, tokens and customer data kept out of prompt files? | scan prompt files for credentials; secret references instead of values | clean | references with plaintext examples | secrets found |

## From the talk

Source: Dex Horthy's talk, [video](https://www.youtube.com/watch?v=8kMaTybvDUw); timestamps are from its caption track. Paraphrase, not a transcript.

- [00:08:36](https://www.youtube.com/watch?v=8kMaTybvDUw&t=516s) Abstractions that write a prompt for you are fine to start, but to get past a quality bar teams end up writing every token by hand ([00:08:58](https://www.youtube.com/watch?v=8kMaTybvDUw&t=538s)).
- [00:09:05](https://www.youtube.com/watch?v=8kMaTybvDUw&t=545s) Reason given: an LLM is a pure function; the only lever on output quality (short of retraining) is the tokens going in, so every prompt choice should be a knob you can test and evaluate ([00:09:20](https://www.youtube.com/watch?v=8kMaTybvDUw&t=560s)).
- Talk-only: stance is "I do not know what is best, so try everything", which supports F02.4 (evals) as the core of the factor rather than prompt style.
